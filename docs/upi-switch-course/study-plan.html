UPI Issuer Switch — Knowledge Source Study Plan

A 16-week program (~8–10 hours/week) that builds the full knowledge base for a bank UPI Issuer Switch: banking fundamentals, NPCI and RBI sources, security standards, distributed-systems engineering, infrastructure, SRE, and the delivery pipeline — with a traceability chain tying it all together.

16 weeks · 12 phases 8–10 hours/week Regulatory traceability matrix Companion to the 20-chapter course
WEEK 1

Phase 0 — Build the Knowledge Map

Before reading specifications, understand the ecosystem. Study these concepts as vocabulary, not depth:

  • Indian banking ecosystem
  • RBI
  • NPCI
  • Banks
  • Issuer
  • Acquirer
  • PSP
  • TPAP
  • Customer
  • Merchant
  • CBS
  • Payment Switch
  • Settlement
  • Reconciliation
  • Dispute
  • Fraud / Risk
  • Authentication
  • Authorization
Output — create the Indian Digital Payments Ontology:
flowchart TD O[Indian Digital Payments Ontology] --> RBI[RBI] O --> NPCI[NPCI] --> UPI[UPI] O --> BK[Banks] --> ISS[Issuer] BK --> ACQ[Acquirer] O --> PSP[PSP / TPAP] O --> CUST[Customer] O --> MER[Merchant] O --> CBS[CBS] O --> SW[Payment Switch] O --> SET[Settlement] O --> REC[Reconciliation] O --> DIS[Dispute] O --> FR[Fraud / Risk]
Rule: do not start architecture yet.
WEEKS 2–3

Phase 1 — Indian Banking Fundamentals

Understand:

  • Banking accounts
  • CASA
  • Customer identification
  • CBS
  • Ledger
  • Debit
  • Credit
  • Holds
  • Available balance
  • Transaction posting
  • Reversal
  • Refund
  • Settlement
  • Reconciliation
  • GL
  • Nostro / Vostro basics
  • Transaction reference numbers
  • Audit trail
The important question you must be able to answer: "When a customer pays ₹1,000 through UPI, what exactly happens inside the bank?"

Trace:

flowchart TD C[Customer] --> A[Mobile App] --> P[PSP] --> N[NPCI] --> S[Bank UPI Issuer Switch] S --> R[Risk / Fraud] --> CB[CBS] --> D[Debit Customer] --> RS[Response] --> N2[NPCI] --> B[Beneficiary Bank]

Then learn what happens when:

  • CBS is unavailable
  • UPI switch is unavailable
  • NPCI is unavailable
  • debit succeeds but response fails
  • response succeeds but debit status is unknown
  • duplicate request arrives
  • reversal arrives
Output: this phase builds your banking transaction ontology.

WEEK 8

Phase 4 — RBI Regulatory Knowledge

Focus on:

  • Payment system regulation
  • Digital payment security
  • Cybersecurity
  • Outsourcing
  • IT governance
  • Operational resilience
  • Data protection / storage requirements
  • Incident management
  • Audit
  • Business continuity
  • Disaster recovery
  • Risk management
Do not simply read RBI documents. For every regulation ask: "What does this mean for my UPI Switch?"
flowchart TD A[RBI Requirement] --> B[Business Requirement] --> C[System Requirement] --> D[Architecture Control] --> E[Implementation] --> F[Test Case] --> G[Evidence]

That transformation is extremely important for a bank project.

WEEK 9

Phase 5 — Payment-Security Standards

Study PCI DSS. Understand:

  • Scope
  • Cardholder data environment
  • Network security
  • Access control
  • Encryption
  • Logging
  • Vulnerability management
  • Secure development
  • Monitoring
  • Incident response
Version note: PCI SSC's current document library lists PCI DSS v4.0.1 — use that rather than older v4.0 material.

Also study:

  • PCI PIN concepts where applicable
  • HSM concepts
  • Key management
  • Cryptography
  • TLS
  • Certificate lifecycle
  • Secrets management
WEEK 10

Phase 6 — Cybersecurity Architecture

Study NIST CSF 2.0 and its six functions:

flowchart LR G[Govern] --> I[Identify] --> P[Protect] --> D[Detect] --> R[Respond] --> RC[Recover]
Note: NIST describes CSF 2.0 as a risk-management framework applicable across sectors and organizations, rather than a prescriptive technology architecture.

Then study:

  • NIST SP 800 series
  • OWASP
  • Secure SDLC
  • Threat modeling
  • Zero Trust
  • Supply-chain security
  • Vulnerability management
  • Secrets
  • IAM
  • PKI
  • HSM
Output: the UPI Switch Security Control Matrix.

The Most Important Part: Don't Study in Isolation

Your study should follow this chain — the knowledge-to-delivery pipeline for the whole program:

flowchart TD REG[REGULATION] --> RBI[RBI] REG --> NPCI[NPCI] RBI --> REQ[REQUIREMENT] NPCI --> REQ REQ --> MRD[MRD] --> BRD[BRD] --> FRD[FRD] --> NFR[NFR] --> ARCH[ARCHITECTURE] ARCH --> SEC[Security] ARCH --> NET[Network] ARCH --> SW[Software] SEC --> HLD[HLD] NET --> HLD SW --> HLD HLD --> LLD[LLD] --> EP[EPICS] --> ST[STORIES] --> DEV[DEVELOPMENT] --> TST[TESTING] --> DEP[DEPLOYMENT] --> PROD[PRODUCTION] --> SRE[SRE] --> MNT[MAINTENANCE]

One Important Change: the Traceability Rule

Replace any "Knowledge Sources" section with this rule:

Rule: Do not merely summarize external standards. Build a traceability chain from each authoritative requirement to the UPI Switch requirement, architecture decision, implementation component, test case, operational control, and audit evidence.

That changes the exercise from a study program into an actual banking-system architecture program. For example:

flowchart LR A[RBI/NPCI requirement] --> B[BRD] --> C[FRD] --> D[NFR] --> E[HLD] --> F[LLD] --> G[User Story] --> H[Code] --> I[Test] --> J[Deployment] --> K[Monitoring] --> L[Audit Evidence]

That is the backbone for the entire bank UPI Issuer Switch program.
